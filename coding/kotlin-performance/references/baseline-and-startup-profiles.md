# Baseline Profiles and Startup Profiles

Load when generating, updating, or auditing Baseline/Startup Profiles for an Android app.

## What they do

- **Baseline Profile** — a text file of Kotlin/Java methods that ART pre-compiles to native code during install (Android 9+) or on first launch. Turns cold-start JIT into fewer, faster paths. Typical: 20–30% cold-start improvement, 15% frame-time improvement.
- **Startup Profile** — a subset used by R8 to lay out DEX so critical startup classes sit in `classes.dex` (loaded first). Stacks on top of Baseline Profile for another 5–15% startup win.

They are **not** the same file, though generated by the same test class.

## Gradle plugin setup

Add the plugin in the module that runs the generator (typically a `com.android.test` module — the same one hosting your Macrobenchmark):

```kotlin
plugins {
    id("androidx.baselineprofile") version "1.4.0"
    id("com.android.test")
    id("org.jetbrains.kotlin.android")
}
android {
    defaultConfig { testInstrumentationRunner = "androidx.benchmark.junit4.AndroidBenchmarkRunner" }
    targetProjectPath = ":app"
}
dependencies {
    implementation("androidx.benchmark:benchmark-macro-junit4:1.4.0")
    implementation("androidx.test.uiautomator:uiautomator:2.3.0")
    implementation("androidx.test.ext:junit:1.2.1")
}
```

Consumer (`:app`):

```kotlin
plugins { id("androidx.baselineprofile") }
android { … }
dependencies {
    "baselineProfile"(project(":benchmark"))
}
```

The `baselineProfile` configuration wires the generator to the app module. AGP places the profile into `assets/dexopt/baseline.prof` at build time.

## Generator test

```kotlin
@RunWith(AndroidJUnit4::class)
@OptIn(ExperimentalBaselineProfilesApi::class)
class BaselineProfileGenerator {
    @get:Rule val rule = BaselineProfileRule()

    @Test fun generate() = rule.collect(
        packageName = "com.example.app",
        includeInStartupProfile = true,   // ALSO produce a startup profile
    ) {
        pressHome()
        startActivityAndWait()

        // Realistic user journey — exercise the actual hot paths
        val feed = device.findObject(By.res(packageName, "feed"))
        feed.setGestureMargin(device.displayWidth / 5)
        feed.fling(Direction.DOWN)
        device.waitForIdle()
        feed.fling(Direction.DOWN)
        device.waitForIdle()

        // Detail navigation
        device.findObject(By.res(packageName, "item-0")).click()
        device.waitForIdle()
        device.pressBack()
    }
}
```

Rules:

- The journey must be **representative**. A test that only launches and idles will produce a startup-only profile, missing scroll/render hot paths.
- Include every major SDK you use: auth, image loader, analytics, network client init — each contributes methods.
- Do **not** synthesize traffic (e.g. call methods reflectively) — only user-driven interactions count as real hot paths.

## Running the generator

```bash
./gradlew :app:generateReleaseBaselineProfile
```

Under the hood:

1. Builds a `nonMinified` app variant that ART can profile freely.
2. Installs on a connected device.
3. Runs the `BaselineProfileRule` test 3 times by default (deduping methods across runs).
4. Extracts the ART profile (`adb shell cmd package dump-profiles <pkg>`).
5. R8 rewrites the human-readable rules to align with the minified release build (Baseline Profile 8.2+ — ~30% additional coverage).
6. Writes to `app/src/main/generated/baselineProfiles/baseline-prof.txt` and `startup-prof.txt`.

Commit both files to the repo.

## Verifying the profile is applied

At install time:

```bash
adb install app-release.apk
adb shell cmd package compile -m speed-profile <pkg>    # apply the shipped profile
adb shell dumpsys package dexopt | grep <pkg>            # verify "speed-profile" was applied
```

In production, `speed-profile` is applied automatically by the Play Store install path; you rarely need this manual step. It matters for local benchmarking of a fresh install.

To measure Baseline Profile coverage inline during a Macrobenchmark:

```kotlin
metrics = listOf(
    StartupTimingMetric(),
    TraceSectionMetric("JIT Compiling %", label = "jit"),
)
```

A low "jit" number = the profile is covering your paths. A high number = missing coverage; rerun the generator with a broader journey.

## Startup Profile specifics

- `includeInStartupProfile = true` in the generator emits `startup-prof.txt` alongside `baseline-prof.txt`.
- R8 reads it and pushes the referenced classes into the primary `classes.dex` — smaller DEX to load first = faster startup.
- Keep the startup profile **narrow**: only cover startup-critical paths. A bloated startup profile defeats the purpose.
- Verify with `apkanalyzer dex packages app-release.apk` — critical startup classes should live in `classes.dex`, not `classes2.dex`.

## Cloud Profiles (advanced)

- Play Store aggregates real-device ART profiles and re-distributes them. Enrolled apps get **Cloud Profiles** that supplement the shipped Baseline Profile.
- Enable via Play Console → App content → "Cloud Profile".
- Cloud Profile input requires committed Baseline Profile as a seed. Add a CI job that runs the generator on top user flows before every release.

## Regression detection

Add a Macrobenchmark run with and without the profile applied, in CI:

```kotlin
@Test fun startup_noProfile() = rule.measureRepeated(
    packageName = "com.example.app",
    metrics = listOf(StartupTimingMetric()),
    iterations = 10,
    startupMode = StartupMode.COLD,
    compilationMode = CompilationMode.None(),        // ← disable the shipped profile
    setupBlock = { pressHome() }
) { startActivityAndWait() }

@Test fun startup_withProfile() = rule.measureRepeated(
    packageName = "com.example.app",
    metrics = listOf(StartupTimingMetric()),
    iterations = 10,
    startupMode = StartupMode.COLD,
    compilationMode = CompilationMode.Partial(),     // ← apply Baseline Profile
    setupBlock = { pressHome() }
) { startActivityAndWait() }
```

Delta between the two = the actual profile impact. Guard against regressions where a refactor accidentally invalidates the profile.

## Anti-patterns

- **Generator run against emulator** → produces a profile biased toward emulator paths. Use physical device.
- **`generateReleaseBaselineProfile` after every code change** → the profile is a snapshot; regenerate on release cadence, not per PR.
- **Missing keep rules for reflection-heavy code** → R8 renames methods that don't appear in the profile because they didn't exist in it. Add explicit `-keep` rules; regenerate profile.
- **Committing only `baseline-prof.txt`, not `startup-prof.txt`** → Startup Profile benefit lost; verify both files are tracked.
- **Assuming the profile applies at first launch on debug builds** → debug builds skip profile application. Test on release/benchmark buildType.
- **Not including callers of `@FastNative`/`@CriticalNative` methods** → these still benefit from being in the profile (see `android-jni-ndk`).
