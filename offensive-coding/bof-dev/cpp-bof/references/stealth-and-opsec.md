# C++ BOF stealth and OPSEC

## Scope

C++ BOFs share the same detection surface as C BOFs, with additional
considerations from the C++ compilation model.

## 1) Runtime-free enforcement

The C++ runtime is the single largest stealth risk in C++ BOFs:

- **Exceptions**: `-fno-exceptions` is mandatory. Any `throw`/`catch` pulls in `__cxa_*` symbols.
- **RTTI**: `-fno-rtti` is mandatory. `typeid`/`dynamic_cast` pull in vtables.
- **STL**: no `<vector>`, `<string>`, `<iostream>`, `<fstream>`. They all need `libstdc++`.
- **Global constructors**: static objects with constructors will **not** run in a BOF. Use explicit init functions.

## 2) Memory hygiene

Same rules as C BOFs:
- No `new`/`delete` — use `HeapAlloc`/`HeapFree` via DFR
- No persistent RWX — always RW → RX flip
- Short-lived decrypted buffers — zeroize after use

C++ RAII wrappers help enforce these rules automatically.

## 3) Import surface minimization

C++ name mangling can accidentally pull in unexpected symbols. Verify with:

```bash
x86_64-w64-mingw32-nm output.o | grep ' U ' | sort -u
```

Any unresolved symbol not matching `MODULE$Function` or `Beacon*` is a problem.

### nm output interpretation

**Clean output example:**

```
         U ADVAPI32$OpenProcessToken
         U KERNEL32$CloseHandle
         U KERNEL32$GetProcessHeap
         U KERNEL32$HeapAlloc
         U KERNEL32$HeapFree
         U MSVCRT$memcpy
         U __imp_BeaconPrintf
         U __imp_BeaconDataParse
```

All `U` (undefined) entries follow `MODULE$Function` or `Beacon*` convention → **clean**.

**Problematic output example:**

```
         U ADVAPI32$OpenProcessToken
         U __cxa_begin_catch          ← EXCEPTIONS LEAKED
         U __cxa_end_catch            ← EXCEPTIONS LEAKED
         U __dso_handle               ← GLOBAL DESTRUCTORS
         U operator new(unsigned long) ← HEAP ALLOCATION
         U __gxx_personality_v0       ← EXCEPTION TABLES
         U KERNEL32$CloseHandle
```

**Symbol diagnosis table:**

| Symbol pattern | Problem | Fix |
|----------------|---------|-----|
| `__cxa_*` | Exception handling runtime | Add `-fno-exceptions` |
| `__dso_handle` | Global destructor registration | Remove static objects with destructors |
| `operator new` | C++ heap allocation | Replace with `HeapAlloc` or `HeapBuf` |
| `__gxx_personality_v0` | Exception unwinding | Add `-fno-exceptions` |
| `__vt_*` / `_ZTV*` | Virtual table | Remove virtual functions or add `-fno-rtti` |
| `_Unwind_Resume` | Exception propagation | Add `-fno-exceptions` |
| `__cxa_atexit` | Static destructor registration | Remove static objects with destructors |
| `__aeabi_*` | ARM-specific (wrong target) | Check `-m64` flag |

**Quick validation command:**

```bash
# Fail if any forbidden symbol appears
x86_64-w64-mingw32-nm output.o | grep ' U ' | grep -E '__cxa_|__dso_handle|operator new|__gxx_personality|_Unwind_Resume|__cxa_atexit' && echo "FAIL: runtime symbols detected" || echo "PASS: clean BOF"
```

## 4) Dual-build testing

Always compile and test both BOF and standalone EXE paths:

- BOF path: validates DFR, Beacon API, and COFF compatibility
- EXE path: validates logic correctness with full debugging

## 5) Template discipline

Templates are zero-cost at runtime but can bloat `.text`:
- Limit template instantiations
- Prefer `constexpr` functions over template meta-programming
- Use `static_assert` for compile-time checks instead of runtime checks

## 6) Build flags for stealth

```bash
x86_64-w64-mingw32-g++ \
    -std=c++17 \
    -m64 -c \
    -O2 \
    -fno-exceptions \
    -fno-rtti \
    -fno-asynchronous-unwind-tables \
    -fno-ident \
    -fpack-struct=8 \
    -falign-functions=1 \
    -ffunction-sections \
    -fdata-sections \
    -fno-merge-constants \
    -s \
    -o output.o \
    -I./assets \
    source.cpp
```

## 7) Indirect syscalls fallback (InlineWhispers3)

When Beacon syscall wrappers are unavailable (non-CS loaders, older CS versions),
use [InlineWhispers3](https://github.com/klezVirus/InlineWhispers3) to generate
indirect syscall stubs compatible with BOF constraints.

Workflow:
1. Run InlineWhispers3 against the target Windows build → `syscalls.asm`
2. Assemble: `nasm -f win64 syscalls.asm -o syscalls.o`
3. Link `syscalls.o` alongside your BOF object
4. Call generated stubs (e.g., `NtAllocateVirtualMemory`) instead of ntdll exports

C++ integration:
```cpp
/* Generated by InlineWhispers3 — declare as extern "C" */
extern "C" {
    NTSTATUS NtAllocateVirtualMemory(HANDLE, PVOID*, ULONG_PTR, PSIZE_T, ULONG, ULONG);
    NTSTATUS NtProtectVirtualMemory(HANDLE, PVOID*, PSIZE_T, ULONG, PULONG);
    NTSTATUS NtWriteVirtualMemory(HANDLE, PVOID, PVOID, SIZE_T, PSIZE_T);
}
```

Limitations:
- SSNs are OS-version dependent → regenerate for target build
- Adds ~2-4 KB per syscall stub to `.text`
- Test against target EDR; some hook the indirect call target in ntdll

## 8) Validation checklist

- [ ] `nm` shows no `__cxa_*`, `operator new`, or `__dso_handle` references
- [ ] No RWX pages in execution flow
- [ ] All handles freed via RAII or explicit cleanup
- [ ] No hardcoded paths or environment-specific data
- [ ] `.text` section size reasonable for the technique
